| Асортимент і перелінковка | висока | прапорці `site_*` + конфіг сайту |
| Сутність магазину (назва, лого, контакти, `Organization`) | середня | `site.config.ts` + `public.{ключ}` |
| Будова сторінок (склад і порядок блоків, розмітка) | середня | варіанти й власні компоненти (§3.2) |
| Візуал (палітра, шрифт, лого, банери, іконки) | для ранжування низька, для людей — головна | тема (§7) |
| Технічний відбиток (класи, `/_nuxt/`, `x-powered-by`, IP) | дуже низька | опційно, етап J (§4.9) |
| Перехресні посилання між сайтами, спільні GA/GSC | шкодить («мережа») | **не робити** |

### 3.2 Три рівні відмінностей

1. **Тема** — `sites/<ключ>/theme.css`: палітра, шрифт, скруглення, тіні, щільність, товщина ліній іконок.
2. **Варіанти** — поля конфігу сайту: склад і порядок блоків головної, шапка (`classic | band | minimal`),
   картка (`bordered | soft | mockup`), розміщення відгуків. Варіант = модифікатор класу або вибір дочірнього
   компонента, не копія.
3. **Власний компонент сайту** — `sites/<ключ>/components/…` з тим самим іменем перекриває рушій (§4.4). Лише
   видимі «обличчя»: шапка, футер, мобільне меню, герой, картка товару/дизайну, плитки, блоки головної, відгуки,
   оболонка чату.

**Правила:** логіка — у рушії (composables), власна версія компонента — лише шаблон і стилі; до ~12 власних
компонентів на сайт; сервісні екрани (кошик, оформлення, підтвердження, конструктор) — спільні, лише тема;
усе — за `CLAUDE.md` (токени, `AppIcon`, `AppImage`, глобальні класи; класи сайту — у його `theme.css`).

## 4. Архітектура рушія для кількох сайтів

### 4.0 Рішення 22.10: кожен сайт — окремий проєкт-копія FLOY

Власник обрав не одну теку `sites/<ключ>/` в одному репозиторії (§4.1–4.2 нижче — початковий задум), а **окремий
проєкт на сайт поруч із FLOY** — `C:\Web-SERVER\domains\SMARKET` (далі так само SotaMARKET, Print-Case). Так
і задумувався крок 1 (`PLAN-SCALING.md`, `brand/README.md` — «як зробити сайт під інший бренд»):
- проєкт = `git clone` FLOY з історією; `upstream` = FLOY, `origin` = свій репозиторій; виправлення рушія
  приходять `git merge upstream/main`;
- своє — лише `brand/` (конфіг, тема, i18n, public, robots) + `brand/components/` (власні компоненти з
  пріоритетом над рушієм) + серверне (`.env`, `ecosystem.config.cjs`, `deploy.sh`);
- загальні зміни рушія, зроблені в копії, — у журнал плану сайту (`PLAN-SITE-SMARKET.md` §10) і переносяться у
  репозиторій FLOY (рушій), щоб копії не розходились; FLOY з ними — піксель у піксель.
- **«Дизайн — окремо, логіка — спільна» (рішення власника 23.10, §16 п. 17).** Візуальна відмінність сайту —
  власна копія компонента в `brand/components/` (шаблон і стилі), не правка рушія: FLOY її не бачить, переносити
  й доводити нічого не треба. Спільний рушій — для логіки: робота з API й адмінкою, кошик, оформлення, оплата,
  доставка, конструктор, чат, SEO, кеш і обробка помилок; саме такі виправлення йдуть загальною зміною у FLOY.
  Загальна зміна не має робити FLOY ні іншим на вигляд, ні важчим чи повільнішим (без нових залежностей і
  запитів). Виняток — токени під світлу тему й подібне, без чого спільні сервісні екрани не працюють у бренді.

Що з §4.1–4.4 лишається в силі: склад теки бренду (замість `sites/<ключ>/` — `brand/` свого проєкту),
перемикачі `features`, власні компоненти, 301-карта, світла основа, шрифти. `SITE=<ключ>` не потрібен —
сайт визначає тека `brand/` проєкту. На сервері — окремий клон на сайт (§11), як і було.

### 4.1 Тека сайту

```
sites/<ключ>/            (sites/floy — нинішній brand/; sites/smarket, sites/sotamarket, sites/printcase)
  site.config.ts      як зараз + features (§4.3), варіанти, шрифти, аналітика, 301-карта (§4.5)
  theme.css           палітра й структурні перевизначення поверх спільної світлої основи (§4.6)
  i18n/{ru,uk}.json   перекриття будь-яких ключів спільних текстів (§8)
  components/         власні версії компонентів (§4.4)
  robots.txt, public/ (лого, фавікони, og, шрифти, файл верифікації GSC)
```

Тека сайту = ключ API: нічого не мапиться.

### 4.2 Вибір сайту

`SITE=<ключ>` при збірці й у dev (`dev.cmd <ключ>`, `build.cmd <ключ>`): аліас `#brand`, i18n, `publicAssets`,
теки компонентів. Без змінної — `floy`. **Приймання:** `SITE=floy` → зліпки проти проду — 0 відмінностей.

### 4.3 Перемикачі розділів (`features`)

Вимкнений розділ прибирається з меню, маршрутів (`pages:extend`), sitemap і точок входу; його адреса — 404
або 301.

| Альфапринти | ✓ | ? | ✓ (основний асортимент: товари `group = alphaprint`) | **—** |
| Неопрінти (свої на сайт) | ✓ | ✓ (додає власник) | ✓ (додає власник) | **✓ основний вміст** |
| Теми-фільтри | ✓ | ✓ | ✓ | ✓ |

| Блог | ✓ | ✓ | ? (0 статей) | ? |

### 4.4 Власні компоненти сайту

Nuxt 3.21: `components: [{ path: sites/<ключ>/components, priority: 10 }, '~/components']` — компонент із
тим самим іменем перекриває рушій. Layers не потрібні. Перший крок етапу C — проба на одному компоненті
(SSR, гідратація, `Lazy`, `hydrate-on-visible`, типи).

### 4.5 Адреси й 301

- **SMARKET, Sota:** схема та сама. 301: `www.` → без www (SMARKET — після перемикання canonical уже
  правильний, змінюється лише напрям редиректу); Sota `/{сторінка}/uk` → `/uk/{сторінка}`; адреси вимкнених
  розділів — як сьогодні. `/printcase/{модель}` — нові сторінки.
- **Print-Case → схема рушія** (рішення 21.10). 301 за шаблонами (не таблицею на 270 тис. рядків), карта —
  у `site.config.ts` сайту, віддає серверний middleware:

### 4.6 Світла тема — спільна основа

`themes/light.css` у рушії, пишеться один раз: `color-scheme: light`, поверхні, межі, тіні, `--tint-rgb: 0, 0, 0`,
`--logo-color`, `--select-arrow`; `--bg-deep` — брендова темна смуга (графіт / синій / чорний), для тексту
на ній — новий токен (`--on-deep`). Перевірка кожного екрана й стану (конструктор, кошик, підтвердження,
чат, лайтбокс, шторки), контраст AA.

### 4.7 Шрифти

Токен шрифту в `main.css`; `@font-face` і `woff2` — у `sites/<ключ>/public/fonts`; preload — з конфігу
(зараз Inter зашитий у `nuxt.config.ts`). Кирилиця + латиниця, 2–3 накреслення.

### 4.8 Тексти

Спільні `i18n/locales/*.json` (579 ключів) → `sites/<ключ>/i18n` перекриває будь-який ключ. Зміст — §8.

### 4.9 Технічний відбиток (опційно, етап J)

Дешево: прибрати `x-powered-by` (nginx), свій `app.buildAssetsDir`. Дорожче: перейменування класів на
збірці (плагін Vite, мапа «клас → хеш із сіллю сайту», виключення — Swiper і HTML з адмінки; перевірка —
`style-snapshot`, попіксельна рівність зі збіркою без перейменування). Лише якщо власник захоче після F–H.

## 5. Дані: прив'язка до сайтів (адмінка)

### 5.0 Правило: одна логіка даних, різниця — лише в теці сайту (рішення власника 22.10)

Усі чотири сайти читають ті самі таблиці тими самими запитами; сайт відрізняється ключем у запиті (`?site=`),
а все інше — це його тека в рушії.

| Шар | Що там | Хто міняє | Як |
|---|---|---|---|
| **БД адмінки** | усе, що веде менеджер: каталог, тексти моделей і тем, товари, дизайни, статті й інфо-сторінки, банери, відгуки, замовлення | менеджер, без деплою | рядок із `site` (лише категорії — спільний рядок + прапорець `site_{ключ}`) |
| **Налаштування `public.common` + `public.{ключ}`** | усе, що менеджер міняє без деплою: спільне — доставка й політики (повернення, строки); свого сайту — ціни конструктора й неопрінтів, контакти з графіком, соцмережі, аксесуари «в набір»; вимикачі (`alphaprint_on_fly`) | менеджер, без деплою | однакова структура в кожного сайту — §5.0.1 |
| **Тека сайту `sites/{ключ}/`** | обличчя й поведінка: назва, домен, лого; тема (палітра, шрифт); варіанти й власні компоненти; тексти інтерфейсу uk/ru; `features`, склад головної, меню, 301, robots, аналітика | розробник, з деплоєм | `site.config.ts`, `theme.css`, `i18n/`, `components/`, `public/` |
| **Рушій** | логіка: запити, сторінки, SEO, кошик, конструктор, чат | розробник | спільний для всіх |

**Правила для даних (однакові для всіх таблиць):**
1. Прив'язка — колонка `site` з ключем із реєстру (`floy`, `smarket`, `sotamarket`, `printcase`); видимість —
   `publish`; порядок — `ordering`.
2. Дві мови — пара колонок `*_uk` / `*_ru` в одному рядку (не окремі рядки на мову); API віддає поле без
   суфікса за `?lang=`.
3. Картинки — файл у `storage/images/{тип}/…`, у БД — шлях від теки типу; нова картинка — нове ім'я файлу
   (сайт кешує картинки за адресою: IPX, nginx).
4. Посилання в даних — шлях від кореня без мови й домену (`/power-bank`); мову й домен додає сайт. Повна
   адреса — лише для зовнішніх.
5. Кеш apisite — ключ із сайтом і мовою; збереження в адмінці чистить саме його.
6. У спільних текстах — не назва й домен сайту, а `{brand}` / `{domain}` (§8).

**Зараз розходиться з правилом** (що виправити — §5.3, §10):
- `public.{ключ}` є лише в `floy`; smarket, sotamarket і printcase живуть на запасних значеннях із конфігу
  рушія — потрібні вузли з тією самою структурою (§10 п. 1). Без вузла адмінка рахує ціну неопрінта й аванс
  сайту за цінами FLOY (`NeoPrintProduct`, `Prepay` беруть `public.floy`), тобто може розійтися з ціною на сайті.
- У блоці `sites` налаштувань адмінки ключ `print-case` замість `printcase` (реєстр, §5.3 п. 1).
- Банери: не було розділу в адмінці (записи вносили в БД руками), посилання в різних форматах (`/printcase`,
  `https://floy.com.ua/power-bank`, `https://steklomarket.com.ua/…`), картинки в корені теки — **виправлено
  22.10, §5.4**.
- Інфо-сторінка `about` у smarket і sotamarket — текст FLOY (дані, §2.3).
- `locales/{site}.json` в адмінці — тексти інтерфейсу старих сайтів (Nuxt 2). На рушії тексти інтерфейсу —
  у `sites/{ключ}/i18n`; адмінські файли живуть, доки працюють старі сайти, рушій їх не читає.

**На межі — перерішено 23.10** (§16 п. 16; 22.10 було «лишити в конфігу»): графік роботи, строки повернення й
доставки (JSON-LD) і аксесуари «в набір» **переходять у налаштування адмінки** — це те, що менеджер міняє без
розробника (аксесуари — разом із цінами й наявністю товарів). Розподіл — §5.0.1.

Новий сайт за цим правилом = запис у реєстрі + тека `sites/{ключ}/` + вузол `public.{ключ}` + дані з
`site = {ключ}` (§18).

#### 5.0.1 Налаштування сайту: що в адмінці, що в коді (23.10; рушій — у SMARKET, журнал `PLAN-SITE-SMARKET.md` §10)

Як це працює: дерево «Налаштування» адмінки → `SettingAction::savePublic` пише для кожного вузла `public.{ключ}`
файл `storage/settings/{ключ}.json` = `array_replace_recursive(public.common, public.{ключ})` → сайт читає його
(`server/api/settings.get.ts`, кеш 5 хв) → `useSiteSettings()`. Сама адмінка теж бере звідси: доставку — лише
з `public.common` (`OrderAction`, `OrderConfirm`, `ApiNovaPochta`), ціну неопрінта й аванс — з `public.{ключ}`.

| Ключ | Рівень | Що | Хто читає |
|---|---|---|---|
| `delivery` | **`public.common`** (сайт не перекриває: адмінка рахує доставку лише зі спільного) | тарифи НП, НП-кур'єр, Укрпошти, самовивозу; поріг безкоштовної доставки | кошик, оформлення, JSON-LD; адмінка |
| `policies` (новий) | **`public.common`** | `return_days` (днів на повернення), `shipping_days` ([від, до] днів НП) | JSON-LD магазину |
| `np_local_db` | `public.common` (адмінка бере з `api.nova_poshta`) | відділення НП зі своєї БД | оформлення |
| `alphaprint_on_fly` | `public.common` або сайт | кадри альфапринтів на льоту | картки, галерея |
| `prices` | **`public.{ключ}`** | конструктор і неопрінт (+ перекреслені), аванс за друк | сайт; адмінка (неопрінт, аванс) |
| `contacts` + `contacts.schedule` (новий) | **`public.{ключ}`** | телефони, пошта, адреса; графік роботи `[{ days, time }]` (`days` — ключ `footer.*` у i18n: `monSat`, `sunday`; `time: null` — вихідний) | шапка, футер, контакти, JSON-LD; приклад номера в підказках форм — перший телефон |
| `social` | **`public.{ключ}`** | соцмережі (порожньо — іконки немає) | футер, JSON-LD `sameAs` |
| `promo_accessories` (новий) | **`public.{ключ}`** (товари в кожного сайту свої) | `[{ id, alias, alias_cat, title: {uk, ru}, image, price, discount, default, only_case? }]` | сторінка товару, «в набір» |

У коді сайту (`brand/site.config.ts`, з деплоєм) — обличчя й будова: ключ, назва, домен, вкладки головної,
`features`, 301-карта, шрифт; і `settingsFallback` — **стартові значення** тих самих ключів: на них сайт живе,
поки його вузла немає, і коли адмінка недоступна, а копії на диску ще немає. Точно збігатися з БД вони більше не
мусять: остання вдала відповідь адмінки лежить на диску процесу (`.cache/settings/{ключ}`, переживає деплой і
перезапуск) і віддається, поки адмінка лежить. До 23.10 запасні значення FLOY уже розійшлися з БД (НП 60 проти
80 ₴, конструктор 289 проти 299) — тепер це не потрапить на сайт.

**Коли зміна з адмінки доходить до сайту** (кожен рівень кешу — свій строк):
1. «Зберегти» в «Налаштуваннях» → одразу `storage/settings/{ключ}.json` і `config/settings.php`; з 23.10
   `SettingAction` ще й перекешовує конфіг Laravel, якщо він закешований (`config:cache` на проді), — інакше
   сама адмінка (ціна неопрінта, аванс, тарифи) рахувала б за старими значеннями до наступного деплою.
2. Сайт перечитує JSON не частіше, ніж раз на **5 хвилин** (кеш процесу; в кожного воркера свій) — нові
   сторінки отримують нові значення не пізніше ніж через 5 хв.
3. **Кеш nginx тримає готові сторінки до доби**, і налаштування в них уже вшиті (payload; з першої сторінки
   ними ж рахує кошик). Щоб зміна була видна одразу всюди — через 5 хв почистити кеш на сервері:
   `find /var/cache/nginx-floy -type f -delete` (SMARKET — `/var/cache/nginx-smarket`).

Нові вузли через SQL (не через форму): після SQL «Зберегти» будь-який запис у «Налаштуваннях» — файли
перебудовує лише збереження з адмінки (`FLOY-ADMIN/NOTES/sql/settings-public-sites.sql`, 23.10).

**Правила:**
1. Спільне для всіх сайтів — лише в `public.common`; своє — лише в `public.{ключ}`. Списки (`phones`,
   `schedule`, `promo_accessories`) — **тільки на одному рівні**: `array_replace_recursive` зливає списки за
   індексами, і довший список із `common` дописав би зайві рядки.
2. Вузол сайту в адмінці — **та сама структура дерева, що й `public.floy`** (папки «ЦІНИ», «Контакти» з окремими
   полями, JSON «Соцмережі», «Аксесуари «в набір»»), щоб редагування в усіх сайтів було однаковим. Новий сайт —
   копією гілки `public.floy` і своїми значеннями: зразок — `FLOY-ADMIN/NOTES/sql/settings-smarket-tree.sql`
   (копіює гілку цілком, з типами й позначками «Н»). Ключі — як у `settingsFallback` (тип — `SiteSettings`,
   `composables/useSiteSettings.ts`). Позначка «Н»: папки — 2 (захищені), значення — 1 (лише редагувати).
3. Новий ключ налаштувань = поле в `SiteSettings` + стартове значення в `settingsFallback` кожного сайту + рядок
   у таблиці вище. Поки ключа немає в адмінці, сайт працює на стартовому значенні — викладати можна в будь-якому
   порядку.

### 5.2 Знайдені проблеми (перевірено 21.10)

1. **`getFilter` не враховує сайт.** `FilterController::getFilter` шукає `Filter::where('alias', …)` без `site`.
   Живий `filters/filter/iphone-16e/anime` для floy, smarket і sotamarket віддає один запис — floy `id 1044`,
   36 шт., тоді як у smarket своя тема `id 4` (47 шт.), у sotamarket — `id 1109` (27 шт.). FLOY отримує свій
   лише тому, що `floy` за абеткою перший в індексі `(alias, site)`. **Сторінки тем SMARKET, Sota й Print-Case
   на новому рушії були б із чужим id, лічильником, текстом і дизайнами.** Те саме в `getProducts`:
   `Filter::whereIn('alias', …)` без `site` (працює випадково — товари й так свого сайту).
2. **Неопрінти рахуються в кожну категорію.** `FilterAction` додає кількість дизайнів теми до `count` у всіх
   рядках `filters_expands` — аксесуарів, брендів, серій, моделей без друку. У БД `printcase = 1` стоїть і на
   категоріях (`power-bank`, `naushniki`) та брендах (`apple`), а рушій перевіряє лише цей прапорець. Наслідок
   **на живому FLOY**: `/power-bank/filter/anime` — h1 «Чехлы с принтом Аниме на Универсальные батареи (Power
   Bank)» і 24 картки «Чехол для … (Power Bank) с картинкой «Kuromi…»»; `/neoprint/power-bank/3891` і
   `/neoprint/apple/3891` — 200. У sitemap FLOY (21.10) тем-сторінок на брендах/серіях — 1 030, на категоріях
   аксесуарів — 90 (×2 мови). Рушій латає це на аксесуарах (`hideThemes`), але не на сторінці теми.
3. **Масовий і одиночний перерахунок розходяться:** масовий бере кількість дизайнів `keyBy('filter_id')`
   з групування `(filter_id, site)` — без звірки з сайтом фільтра; одиночний звіряє.
4. **`filters_expands` — щільна матриця** «кожен фільтр × кожна категорія»: рядки створюються для всіх
   категорій при створенні фільтра (`Filter::created`) і для всіх фільтрів — при створенні категорії, хоча
   більшість мають `count = 0` і порожній опис. Свої теми на 4 сайтах множать її. Перерахунок робить upsert
   по всіх рядках фільтра. Розмір — звірити на проді (`COUNT(*)`, частка `count = 0` без опису).
5. **`getFilter` не кешується** (на відміну від `getFilters`) і щоразу тягне товари фільтра й відгуки.
6. **Ключ сайту в назві колонки.** `site=print-case` → колонка `site_print-case` → 500 (так і є зараз).
   Тому ключ Print-Case — **`printcase`** (збігається з колонкою, `SearchEngine`, ШІ-інструментами; старі
   замовлення з `print-case` лишаються історією — у статистиці показувати обидва під однією назвою).
   `BaseApiSiteController` бере `site` із запиту без перевірки — потрібен білий список.
7. ~~`getNeoPrint` без `site`~~ — *уточнено 21.10:* API віддає дизайн будь-якого сайту, але сторінка
   `/neoprint/…` рушія сама звіряє `neoprint.site` із сайтом і дає 404. Чужий дизайн не відкривається;
   правити API не обов'язково.
8. **Форма атрибута:** при зміні сайту список тем перезавантажується, але вибрана тема (`filter_id`) не
   скидається; на сервері немає перевірки «тема того ж сайту, що й дизайн». Клон на інший сайт лишає тему
   старого сайту. **Гірше (знайдено 21.10): сайт атрибута взагалі не зберігався** — у правилах
   `Attribute\StoreUpdateRequest` не було `site`, `validated()` його відкидав. Створений або клонований
   через форму дизайн лишався на сайті за замовчуванням; сайт ставило лише масове завантаження
   («Смарт-атрибути»).
9. **Сайти зашиті списками в ~15 місцях адмінки:** `ReviewController` (білий список `floy/smarket`,
   `site_url`), `SearchEngine` і `FindModelTool` (`floy/smarket/printcase`, решта → floy), `AdminModelSearch`,
   `CategoryAction`, `ModelAI`, `MetaTagsUtil`, `SitemapGenerator` (лише floy), `SitemapUtil`, `SeoLinksScan`,
   `SeoAction`, `SeriesOrderStat`, `BrokenImagesScan`, `CacheUtil`, `OtherUtil`.

### 5.3 Що виправити (адмінка)

1. **Реєстр сайтів** `config/sites.php` (ключ, домен, URL, назви для ШІ, колір для статистики, `features`) —
   усі місця з п. 9 читають його; `BaseApiSiteController` пускає лише ключі з реєстру (решта — 404).
   **26.10 (SMARKET S7):** реєстр — клас `App\Actions\SiteRegistry` (ключ, назва, URL, назва й персона для чату), а не
   `config/sites.php`: конфіг на проді закешований, і новий файл до `config:cache` читався б порожнім — apisite дав би
   404 усім сайтам. З реєстру вже читають `BaseApiSiteController`, `SearchEngine` (sotamarket більше не шукає в товарах
   FLOY), `FindModelTool`, `ReviewController` (`sendReview`, `site_url`), `PromptBuilder`. Решта списків — у шапці класу.
2. **Фільтри — завжди з `site`:** `getFilter`, `getProducts` (і всюди, де фільтр шукається за alias).
3. **Неопрінти рахуються лише в моделі, що друкуються:** `type = 'model'` і `printcase = 1`. Тоді теми
   зникають з аксесуарів, брендів і серій, а `count` дорівнює тому, що реально видно. Статус друку
   (`alphaprint_available`) у лічильник не входить: він змінюється частіше за нічний перерахунок.
   Прапорець `printcase` на не-моделях код тепер просто ігнорує (перевірка типу); чистити дані не обов'язково.
4. **Перерахунок:** дизайни — за парою `(filter_id, site)` зі звіркою з сайтом фільтра; одна функція для
   масового й одиночного.
5. **`filters_expands` — розріджено:** рядок лише там, де `count > 0` або є опис. Не створювати рядки «на
   всі категорії» в хуках; перерахунок — set-based SQL по сайту (`INSERT … SELECT … ON DUPLICATE KEY UPDATE`)
   + обнулення/видалення застарілих рядків без опису. Перед і після — `COUNT(*)` і час перерахунку на проді.
6. **Кеш `getFilter`** (`site + категорія + фільтр + мова`), як у `getFilters`.
7. **`getNeoPrint` — з `site`** (чужий → 404); `neo_prints` — пагінація й кілька тем за раз (§6.2).
8. **Форма атрибута:** при зміні сайту — тема скидається або підбирається тема того самого alias на новому
   сайті (`anime` → `anime`); те саме при клонуванні; на сервері — валідація «сайт теми = сайт дизайну».
9. **Ключ `printcase`**, `public.printcase`; відгуки (`sendReview`) і пошук — з реєстру.

Масштабування: п'ятий сайт = запис у реєстрі + колонка `site_<ключ>` у `categories`. Якщо сайтів стане
більше — перейти з колонок на таблицю `categories_sites` (до того не варто).

## 6. Неопрінти по сайтах і сторінка моделі з дизайнами

### 6.1 Правила неопрінтів (рішення 21.10: у кожного сайту свої)

- Неопрінт = атрибут `type = neo_print` з `site`. Дизайни на сайтах **не повторюються**: власник додає окремі
  набори для кожного сайту. Тема дизайну — фільтр **того самого сайту** (§5.3 п. 8).
- Alias = id (глобально унікальний) → адреси `/neoprint/{модель}/{id}`, файли шаблонів і кеш кадрів
  `/img/neoprint` не конфліктують між сайтами. Кеш кадрів може лишатись спільним.
- Чужий дизайн на сайті — 404 (§5.3 п. 7). Опис дизайну (`description_*` з `#model#`) — свій у кожного запису.
- Альфапринти — окремий тип (`alpha_print`), на Print-Case їх немає.

### 6.2 Режим «дизайни» на сторінці моделі — робимо спершу на FLOY

**Навіщо.** Print-Case не має товарів: його сторінка моделі = дизайни з пагінацією. На FLOY та сама логіка
закриває моделі без товарів (зараз це рідкість: на нових моделях 130–150 товарів, але є моделі з 5–14
товарами; без генерації нових товарів таких ставатиме більше).

**Статуси друку моделі** (`categories.alphaprint_available`, логіка — `modelPrintState` у
`useProductHelpers`): `available` і **`available_not` — друкуємо одразу** (`available_not` ≠ «знято»!),
`pre_order` — лише передзамовлення, **`not_available` — модель знято з друку**.

**Правило (одне для всіх сайтів):**
- «на модель друкуємо» — `canPrintOn(category)`: `type = model` і `printcase`. Від цього залежать
  неопрінти на сторінках тем, сторінка `/neoprint/…` і лічильники (бекенд — `FilterAction::printableCategoryIds`);
- **сітка дизайнів** замість порожнього стану: `canPrintOn` + статус не `not_available` + сторінка самої
  моделі (без `/filter/` і `?filter_*`) + API товарів відповів і товарів 0 (на Print-Case — завжди);
- інакше — як зараз (товари; дизайни — на сторінках тем).

**Як зроблено (21.10, рушій):**
- **Без змін API адмінки:** повний список дизайнів сайту вже тягнувся й перемежовувався за темами в Nitro
  для конструктора. Тепер це спільна утиліта `server/utils/siteDesigns.ts` (кеш година, порожній список не
  кешується). `/api/printcase/designs` бере з неї перші 24 (результат побайтно як на проді), новий
  `/api/neoprints?page&limit` — сторінку `{ data, meta }` у формі списку товарів.
- `CategoryPage`: `designsMode`; пагінація, «показати ще» й автопідвантаження — того списку, що на
  сторінці; `?page` поза межами → 404; перша картка — конструктор; лічильник «N готових дизайнів»;
  сортування сховане; лід `modelLead.designs` і таблиця цін із дизайнів на сторінці 1; `ItemList` —
  посилання на дизайни; og:image — перший дизайн.
- **Індексація (рішення 21.10):** сторінка 1 індексується, **сторінки ≥ 2 — `noindex, follow`**
  (canonical свій, `?page=N`).
- **Захист від безглуздих сторінок:** дизайни на сторінках тем і `/neoprint/…` — лише `canPrintOn`
  (`/neoprint/apple/…`, `/neoprint/power-bank/…` → 404); FAQ теми веде в конструктор лише на моделі;
  **сторінка фільтра без товарів і дизайнів → 301 на категорію** (лише 1-ша сторінка, без `?filter_*` і
  лише коли API товарів відповів — збій не стає постійним 301). Так уже проіндексовані

**Ще не зроблено** (не потрібно для FLOY, знадобиться Print-Case): `features.products = false` (не робити
запит товарів), чипи тем над сіткою, FAQ у варіанті «дизайни». Моделей без товарів на FLOY зараз немає

### 6.3 Сторінка теми

- `/{модель}/filter/{тема}` — як зараз (товари + дизайни теми); у режимі «дизайни» — та сама сітка з
  пагінацією замість «показати ще» (зараз до 240 + кнопка). На FLOY «показати ще» для сторінок із товарами
  поки лишається — змінювати після оцінки.
- `/chekhly/filter/{тема}` — тема без моделі (аналог `/theme/{тема}` Print-Case): картка показує сам дизайн
  (мініатюру шаблону) і веде на вибір моделі (`ModelSelectModal`) → `/neoprint/{модель}/{id}`. Нова поведінка,
  потрібна Print-Case; на FLOY — за рішенням.

### 6.4 Print-Case — лише неопрінти

- Дані: теми PC → фільтри `site = printcase` (alias PC зберігаємо — 301 тривіальні); шаблони PC →
  неопрінти `site = printcase` (+ мапа «alias шаблону → id» для 301); товари PC не переносимо — їх заміняє
  «модель × дизайн» на льоту. Спершу звірити шаблони PC з неопрінтами FLOY: спільні дизайни на двох сайтах
  — дубль, їх або не переносити, або прибрати з одного з сайтів.
- Моделі: `site_printcase = 1` лише моделям, що друкуються.
- Головна: популярні дизайни — потрібен ендпоінт популярності (за замовленнями `attribute_id`, кеш на добу).
- Sitemap: моделі, теми на моделях, теми без моделі, конструктор моделей. Сторінки «модель × дизайн»
  (~400 моделей × сотні дизайнів) — не в sitemap, до них ведуть сітки. Рішення — у плані сайту.

### 7.1 Відмінність від FLOY лише стилями — рецепт (досвід SMARKET 27.10)

Подробиці й стан — `PLAN-SITE-SMARKET.md` §4 «Форма». **Навіщо:** палітра й власні компоненти (шапка, головна,
картки) роблять сайт іншим лише там, де вони є. Спільні екрани рушія (товар, конструктор, бокове меню, крихти, чипи)
і **форма** (скруглення 8/14/20 з `main.css`) лишаються FLOY-івськими — власник 27.10: «дуже схожий на флой
(однакові скруглення)». Копіювати ці компоненти в бренд не можна (`ProductPage` — 860 рядків, ~500 логіки; межа
12 перекриттів), тож — стилями. Рушій не змінюється, переносити у FLOY нічого.

**Механізм:**
- `brand/overrides.css`, підключений `@import './overrides.css';` на початку `brand/theme.css` (до `@font-face`:
  `@import` — лише перед усіма правилами); рядок у `brand/README.md`.
- **Форма — токенами** в `theme.css`: `--radius-sm`, `--radius`, `--radius-lg`. У рушії й бренді скруглення вже всі
  через них (літерали — лише дрібниці 2–6 px; `calc(var(--radius-sm) - 4px)` при 4 дає 0 — нормально).
- **Специфічність, а не порядок:** scoped-правило рушія — його класи + 1 (`[data-v-…]`), і в dev до гідратації
  `<link>` теми йде раніше за `main.css` і компоненти. Тому перекриття — на клас вище: базове правило (`.x[data-v]`) —
  двома класами з батьком (`.product__buy.card .product__actions`), стан (`.x.is-active[data-v]`, `.x[data-v]:hover`) —
  трьома. Перед перекриттям — прочитати scoped-стилі компонента й порахувати.
- **Глобальні класи `main.css`** (`.btn`, `.chip`) — тим самим одним класом і лише база: стани рушія (`.chip:hover`,
  `.chip.is-active` — два класи) мають лишитися сильнішими, інакше наведення зникне. Глобальне правило, де станів
  немає (`.section-title::after`, `.breadcrumbs .sep`), — через `:root …`.

**Що на спільних екранах видає FLOY** (чек-лист; праворуч — як зроблено в SMARKET, **не копіювати**: сайти мають
відрізнятися й між собою, §3 — кожному свою мову форми):

|---|---|---|

- **Елемент не в тому контейнері** (посилання конструктора в розмітці — після картки ціни, а треба всередині):
  від'ємний відступ на точно відомі висоти (кнопкам — явна `height`), лише під `:has()`
  (`.product__buy.card:has(.product__quick) + .product__printcase`): без `:has()` старий браузер лишає звичайне
  розташування, без «Швидкого замовлення» (передзамовлення) — теж. Де навпіл не вміщується (SMARKET — ≤ 1180 px),

  емуляцією** (headless Chrome без неї не вужчий за ~500 px); консоль і гідратація — 0.
- **Наступним сайтам:** `brand/overrides.css` SMARKET — заготовка будови (селектори й специфічність перевірені), але
  значення — свої. Напрям для обговорення з власником: SotaMARKET («Вітрина+», Nunito) — м'якша форма, Print-Case
  («Темна вітрина+») — гостріша; рішення — у §3 плану сайту.

## 8. Тексти й локалізація — «свій голос»

**Тон:** SMARKET — експерт, на «ви», коротко; Sota — на «ти», легко (як нинішній SEO-текст головної);
Print-Case — емоційно, про ідею й подарунок.

**Що перекриваємо в `sites/<ключ>/i18n` (за вагою):** SEO-шаблони (`faq`, `modelLead`, `filterLead`,
`neoprint`, SEO-частини `printcase`, `pageTitle`/`metaTitle`/`metaDescription`, `productTags`) → видимі
заголовки й дії (`index`, `header`, `footer`, `category`, `product`, `reviews`, `search`, `error404`,

- **Просідання трафіку після перемикання** (нові шаблони, title без суфікса, зникнення зірок) — найсильніше
  на SMARKET; тому він після пілоту.
- **Дублі між сайтами:** спільні статті адмінки (уже є), шаблони без перекриття i18n, однакові дизайни на двох
  сайтах — ловить тест унікальності.
- **Етап 0 на FLOY:** зміна лічильників і 301 зачіпає ~2,2 тис. адрес — робити зі зліпками до/після.
- **Обслуговування власних компонентів ×4** — правило «логіка в рушії» і ліміт.
- **Світла тема** зачіпає всі екрани, зокрема великі (конструктор, оформлення).
- **Пам'ять сервера** під час паралельної роботи старих сайтів і стендів.
- **Пастки:** `.env` у git; `ecosystem`/`cluster.mjs`; `location` для robots; ручна правка на сервері зупиняє
  `git pull`; `throwIfApiDown`; кеш `categories/category/{alias}` в apisite — добу.

## 18. Як додати ще один сайт (перевірка масштабованості)

Адмінка: запис у `config/sites.php` → колонка `site_<ключ>` у `categories` → вузол `public.<ключ>` → свої
теми й неопрінти → тексти, мета-шаблони, статті. Рушій: тека `sites/<ключ>/` (конфіг, тема, i18n, лого,
власні компоненти — за потреби). Сервер: клон, порт, процес, вхост. Нічого в коді рушія не перелічує
сайти — якщо для нового сайту довелося правити рушій чи список у адмінці, це дефект реєстру.
