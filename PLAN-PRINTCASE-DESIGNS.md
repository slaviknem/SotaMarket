# Збереження макетів конструктора чохлів — мінімальний варіант (без БД)

> **Статус: реалізовано 2026-08-16.** Бекенд перевірено локально (`php artisan serve` + curl):
> створення макета, перезбереження під тим самим id, відмова на чужий токен, чистка за розкладом.
> Фронт зібрано компілятором SFC, у браузері ще не проганявся — потрібен `dev.cmd`.
>
> Відхилення від плану (усі — у бік простоти чи надійності), деталі в §14: маніфест читається
> ручкою API, а не зі сховища (там на `.json` — 403); імʼя файла-фото перевіряється форматом,
> а не звірянням хеша; `upload_image` блокує лише перезапис файлів, старших за 5 хвилин.

## 1. Рішення одним абзацом

Ніякої таблиці й міграції. **Ідентифікатор макета вже існує** — це число з
`orders_items.printcase` (`…/orders/source_{id}.jpg`), яке адмінка вже витягує регуляркою
([ItemProduct.vue:183](../FLOY-ADMIN/resources/js/views/Order/FormOrder/ItemProduct.vue#L183)).
Достатньо покласти поруч із результатом папку з «сирцями» під тим самим id — і все зв'язується
саме собою. Чернетки живуть у браузері (IndexedDB) і не створюють на сервері нічого.

| Що | Де | Скільки живе |
|---|---|---|
| Результат друку `source_{id}.jpg` + прев'ю | `storage/…/printcase/orders/` — **як зараз** | завжди (передрук з адмінки) |
| Фото клієнта (зжаті) + `state.json` | `storage/…/printcase/designs/{id}_{token}/` | **30 днів**, далі видаляє крон |
| Незавершений макет | IndexedDB браузера клієнта | 30 днів, чистить сам браузер |

Наслідки: **0 міграцій, 0 моделей, 0 змін у кошику, у `sendOrder`, у форматі замовлення
і в друкарському конвеєрі** (`CaseShopCaseBinder` продовжує читати `source_{id}.jpg`).

## 2. Розкладка файлів

```
storage/app/public/images/printcase/
  orders/                       ← НЕ ЧІПАЄМО
    source_1754300000.jpg       ← результат, іде у друк
    preview_1754300000.jpg      ← прев'ю для кошика/адмінки
  designs/
    1754300000_a91f3c7d/        ← {id}_{token}: id = час створення, token = HMAC(id, APP_KEY)
      state.json                ← маніфест: тексти, координати, фон, посилання на фото
      9f2c41ab8d3e5170.jpg      ← фото клієнта (ім'я = sha файлу)
      c05d19ee7a44b382.png
```

Чому `{id}_{token}` в імені папки, а не просто `{id}`:

- id — це unix-час, його легко підібрати перебором, а всередині лежать **особисті фото клієнтів**.
  Токен (10 hex) робить папку невгадуваною, і при цьому його не треба ніде зберігати —
  сервер і адмінка рахують його з id за `APP_KEY`;
- id перед підкресленням = час створення, тож **чистка не робить жодного `stat`**:
  `if ((int) explode('_', $dir)[0] < time() - 30*86400) → видалити`.

## 3. Маніфест `state.json`

Це те, що вже лежить у пам'яті редактора (`elements` + `backgroundColor`), тільки замість
`data:`-URL — посилання на файл:

```json
{
  "v": 1,
  "stage": { "w": 400, "h": 800 },
  "model": "samsung-galaxy-a07",
  "bg": "#FFFFFF",
  "els": [
    { "t": "img", "src": "sha:9f2c41ab8d3e5170",  "x": 12, "y": 130, "w": 375, "h": 500, "r": -8 },
    { "t": "img", "src": "lib:flowers/rose.png" },
    { "t": "img", "src": "neo:kvity-125" },
    { "t": "txt", "s": "Аня", "f": "Lobster", "c": "#000000", "b": true,
      "x": 100, "y": 600, "w": 200, "h": 44, "r": 0 }
  ]
}
```

- координати — **у координатах сцени 400×800**, тобто рівно як у `StageEl` (жодних перетворень);
- три види джерел: `sha:` — файл клієнта в цій же папці, `lib:` — бібліотека конструктора,
  `neo:` — готовий дизайн. Два останні вже вміє відновлювати наявний код (`imageB64`, рядок 1067);
- `v` — версія формату (щоб через рік можна було мігрувати, а не ламати старі макети);
- `activated` не пишемо (це стан виділення), `hidden` пишемо;
- вага — 1–3 КБ.

## 4. Стиснення фото (щоб не впливало на друк)

Друк рендериться у **800×1600** (`renderCanvas(800)`), сцена — 400×800.
Фото з телефона — 3000–4000px і 2–5 МБ, тобто в 4–5 разів більше, ніж узагалі можна надрукувати.

**Правило:** при додаванні фото в редактор одразу зменшуємо до **2000px по довшій стороні,
JPEG q0.85**. Це 2.5× запас над шириною друку — навіть якщо клієнт наблизить фото втричі,
роздільності вистачає з головою. Типовий результат — 300–600 КБ замість 2–5 МБ.

Винятки:
- файл уже ≤2000px і <1 МБ → **не чіпаємо взагалі** (нуль втрат, нуль CPU);
- PNG з прозорістю → лишається PNG (наліпки, вирізані об'єкти).

Стискаємо **в браузері при додаванні**, а не на сервері. Три виграші однією функцією:
редактор перестає тримати в пам'яті 5-мегабайтні `data:`-рядки, чернетка в IndexedDB стає
маленькою, і заливання на мобільному пришвидшується вп'ятеро.

> Побічний бонус: коли оригінали 2000px лежать на сервері, можна безболісно підняти
> рендер друку з 800 до 1200–1600px. Не обов'язково зараз, але шлях відкривається.

## 5. Потік: клієнт малює → в кошик

**Під час малювання** (нічого на сервер не йде):

1. фото додано → `prepareImage()` зменшує → `Blob` + `sha` (перші 16 hex від SHA-256);
2. елемент тримає `blob:`-URL (замість теперішнього `data:`) — canvas із ним працює так само;
3. будь-яка зміна → через 1,5 с автозбереження маніфесту + блобів **в IndexedDB**,
   ключ `printcase:draft:{модель}`.

**«В кошик»** — замість двох теперішніх POST стає **один блокуючий**:

```
POST apisite/printcase/save_design
     { state, preview, source }          ← прев'ю та джерело як зараз, base64
  →  { id, token, preview, source }      ← сервер сам обрав вільний id
```

Сервер пише `orders/source_{id}.jpg`, `orders/preview_{id}.jpg`, `designs/{id}_{token}/state.json`.
Кнопка кошика розблоковується — далі все як сьогодні (`cart.add` не змінюється).

**Фото — у фоні, після цього:**

```
POST apisite/printcase/save_asset   (multipart: dir={id}_{token}, sha, file)
```

Якщо клієнт закрив вкладку раніше — у замовленні лишається готовий `source.jpg`,
тобто **не гірше, ніж сьогодні**. Це важлива властивість: фонове довантаження нічого не ламає.

Заодно зникає наявний баг: `id = Date.now()/1000` генерувався **на клієнті**, і два замовлення
в одну секунду перезаписували друк одне одному. Тепер id обирає сервер (шукає вільну папку).

## 6. Потік: клієнт повернувся через тиждень

Заходить на `/printcase/{модель}` → composable бачить чернетку в IndexedDB → відновлює
елементи з блобів (миттєво, без мережі) і показує зверху смужку:

> Відновлено ваш попередній макет · **Почати заново**

Мовчки не відновлюємо (людина могла прийти робити новий чохол) і питати заздалегідь теж
не варто — зайвий клік. Правила зберігання: **останні 5 макетів (LRU), TTL 30 днів,
стеля ~150 МБ**; при `QuotaExceededError` тихо викидаємо найстаріший. Після успішного
«В кошик» чернетка цієї моделі чиститься.

Чому браузер, а не сервер:

| | IndexedDB **(обрано)** | Серверна чернетка |
|---|---|---|
| Код | один composable, ~100 рядків | + ендпоінт, + токени, + антиабʼюз, + чистка покинутих |
| Місце на сервері | **0** | покинутих макетів у 3–5 разів більше, ніж замовлених → ~2–5 ГБ постійно |
| Швидкість відновлення | миттєво, офлайн | запит до API |
| Інший пристрій | ні | так |

`localStorage` тут не підходить у принципі: там ~5 МБ на домен, одне фото не влізе.
IndexedDB тримає блоби без такого обмеження.

Єдиний мінус — «намалював на телефоні, доробляю на компі» не працює. Якщо колись знадобиться,
той самий `save_design` вміє зберегти чернетку — це +15 рядків, але вже з платою за місце.

## 7. Потік: редагування з адмінки

**Кнопка.** У `ItemProduct.vue` поруч із чипом «індивід. друк» — олівець. Показуємо його
**лише якщо id молодший за 30 днів** (id — це час, перевірка чисто клієнтська, без запитів):

```html
<a v-if="canEditDesign" :href="`/order/printcase-edit/${designId}?cat=${item.category.alias}`"
   target="_blank" class="attr-chip__edit" title="Редагувати макет">✎</a>
```

**Редірект в адмінці** (`routes/web.php`, ~8 рядків): рахує токен із id за `APP_KEY` і
відправляє на сайт:

```
https://floy.com.ua/printcase/{модель}?design={id}_{token}
```

Токен ніде не зберігається — він завжди виводиться з id. Тому й не потрібна колонка в БД.

**Сторінка конструктора з `?design=`:**

1. тягне маніфест ручкою `printcase/get_design/{id}_{token}` (сховище віддає з-під веб-сервера
   лише картинки — на `.json` там 403, тож читає його сам Laravel);
2. фото відновлює наявним ендпоінтом **без жодного нового коду на бекенді**:
   `printcase/get_image_b64/{sha}.jpg/designs/{id}_{token}` — маршрут уже вміє довільну підпапку
   і віддає base64, тобто canvas не «отруюється» (те, чим уже користуються маска й бібліотека);
3. режим правки: шапка «Редагування макета замовлення», кнопка замість «В кошик» —
   **«Зберегти зміни»**, сторінка `noindex` (умова вже є для `?order_id=`, дописуємо `design`);
4. збереження — **той самий** `save_design`, але з `id` і `token`: сервер перезаписує
   `orders/source_{id}.jpg` + `preview_{id}.jpg` і `state.json`.
   Друк і CaseShop підхоплюють новий файл, бо шлях не змінився.

**Якщо папку вже видалено** (>30 днів) — олівця просто немає, а прямий вхід показує:
«Оригінали цього макета видалено (зберігаються 30 днів). Передрук доступний із готового
зображення». Передрук завжди працює — `source_{id}.jpg` лежить вічно.

**Дрібне, але критичне:** перед `renderCanvas` треба `await document.fonts.ready`.
Зараз цього немає; при звичайному малюванні шрифти встигають (людина малює хвилинами),
а от менеджер, що відкрив макет і одразу натиснув «Зберегти», гарантовано отримає
у друк Arial замість Lobster. Один рядок.

**Кеш прев'ю в адмінці:** оскільки сховище зараз віддається **без `Cache-Control`**
(див. `NOTES/PLAN-IMAGES.md`), браузер підтягне оновлену картинку сам. Якщо колись додасте
кеш-заголовки — тоді ж треба буде додати `?v=` до `printcase`/`image_file`.

## 8. Чистка: 30 днів

`app/Console/Commands/PrintcaseCleanup.php` — уся суть команди:

```php
$edge = time() - 30 * 86400;
foreach (Storage::disk('public')->directories('images/printcase/designs') as $dir) {
    $id = (int) explode('_', basename($dir))[0];
    if ($id && $id < $edge) Storage::disk('public')->deleteDirectory($dir);
}
```

Жодних `filemtime`, жодного обходу файлів — ім'я папки вже містить дату.
У `Kernel.php` (там уже є `hourly`/`daily` блоки) — `->dailyAt('04:00')`.
Термін винести в `config` або в налаштування адмінки, щоб міняти без деплою.

Папки покинутих макетів (зберігся, але в кошик не поклали) чистяться тим самим правилом —
окрема логіка не потрібна.

## 9. Безпека і ліміти

- **закриваємо наявну діру:** зараз `upload_image` приймає `id` від клієнта й мовчки
  перезаписує `source_{id}.jpg` **будь-якого** замовлення. У `save_design` перезапис можливий
  лише з валідним токеном; без токена сервер завжди створює новий id.
  Старий `upload_image` лишаємо (ним користуються steklomarket/sotamarket), але додаємо
  три рядки: «немає токена → писати тільки якщо файлу ще не існує»;
- `throttle:20,1` на `save_design`, `throttle:60,1` на `save_asset`;
- ліміт 8 МБ на файл, тип перевіряти `getimagesize`, а не заголовком запиту;
- ім'я файлу активу — **тільки sha, порахований сервером** із прийнятих байтів
  (клієнтський sha звіряємо; не збігся — 422). Жодних імен зі шляхом із запиту;
- у `config/cors.php` замінити точковий `apisite/printcase/upload_image` на `apisite/printcase/*`
  (CSRF для `apisite/printcase/*` уже виключено).

## 12. Порядок робіт

1. **Бек**: `saveDesign` + `saveAsset` + cors + throttle. *(пів дня)*
2. **Фронт, збереження**: стиснення фото, sha, маніфест, новий `generateAndUpload`,
   фонове довантаження активів.
   → **з цього моменту оригінали й координати вже не втрачаються**, навіть без редагування. *(день)*
3. **Редагування з адмінки**: режим `?design=`, «Зберегти зміни», `get_design`, олівець, `document.fonts`. *(день)*
4. **Чернетки**: IndexedDB + смужка «відновлено». *(день)*
5. **Чистка**: команда + розклад. *(година)*

Кроки 1–2 самодостатні: навіть якщо зупинитись на них, будь-яку правку можна зробити руками
з файлів у `designs/{id}_{token}/`.

## 13. Що треба зробити при викладці

1. **Адмінка**: перезібрати фронт (`npm run build` — Vite), бо змінився `ItemProduct.vue`.
2. **Кеш конфігів**: змінились `config/cors.php` і маршрути — якщо на проді вони кешовані,
   `php artisan config:cache && php artisan route:cache`.
3. **Ліміти веб-сервера**: `save_asset` приймає файл до 8 МБ — потрібні
   `client_max_body_size` ≥ 10M у nginx і `upload_max_filesize`/`post_max_size` ≥ 10M у PHP.
   (`save_design` шле ~0,5 МБ base64 — це вже працює сьогодні.)
4. **Крон** уже налаштований — `printcase:cleanup` стане в чергу автоматично (04:00).
   Перший запуск варто зробити руками з `--dry`, щоб побачити, що саме він видалить.
5. **Сайт**: `build.cmd` (як завжди, вручну).

Порядок безпечний: якщо викласти адмінку раніше за сайт, старий фронт і далі шле
`upload_image` і працює як раніше; якщо сайт раніше за адмінку — `save_design` віддасть 404
і кнопка кошика покаже помилку, тож **спершу адмінка**.

## 14. Відхилення від початкового плану

| Було в плані | Як зроблено | Чому |
|---|---|---|
| Сервер звіряє sha фото з клієнтським | Перевіряє лише формат імені (`16 hex + jpg/png/webp`) | WebCrypto немає поза https/localhost (дев по локальній мережі), а сувора звірка ще й ламала б макет, коли розширення файла бреше про його вміст. Захист від сторонніх імен дає регулярка, від чужої папки — токен |
| `upload_image`: писати лише якщо файлу ще немає | Забороняє перезапис файлів, **старших за 5 хв** | Інакше повторний клік «В кошик» у ту саму секунду ламав би замовлення на steklomarket/sotamarket, які досі шлють цю ручку |
| Маніфест читається зі сховища через проксі Nitro | Читається ручкою `get_design` адмінки; проксі видалено | **Знайдено на проді:** веб-сервер віддає зі сховища лише картинки, на `.json` — 403. Заразом і простіше: CORS для `apisite/printcase/*` уже відкритий, зайвий шар не потрібен |
| Олівець в адмінці для всіх замовлень до 30 днів | Плюс перевірка «id ≥ дати запуску» | Інакше на замовленні, зробленому до викладки, менеджер відкривав би порожній конструктор |
| `createImageBitmap` / `crypto.subtle` напряму | Обидва з фолбеком (`<img>` та простий хеш) | Інакше в старих Safari і в деві по локальній мережі фото просто не додавалося б |

## 15. Свідомі компроміси

| Спрощення | Чим платимо | Чому прийнятно |
|---|---|---|
| Без БД, id із імені файлу | не можна одним SQL спитати «скільки макетів за місяць» | статистика тут не потрібна; папки й так видно |
| Чернетка тільки в браузері | не переноситься між пристроями; чистка кешу = втрата | сценарій рідкісний, а ціна — нуль коду й нуль місця на сервері |
| Фото стискаються до 2000px | якщо колись друкуватимете у 4000px — запасу не буде | друк 800×1600; 2000px — 2.5× запас |
| Активи живуть 30 днів | через місяць правка неможлива, лише передрук | рівно те, що просив замовник |
| Фонове довантаження фото | вкладку закрили одразу → активів немає, лише результат | не гірше за поточну поведінку |
